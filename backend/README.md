# OmniCloud authentication backend

This backend provides account registration, email verification, password sign-in, password reset by email code, and persistent login sessions. Registration details and the verification code are held in backend memory until the code is accepted; no user row or verification code is written to MySQL before verification. After successful verification, the backend creates the verified user row and login session. Pending registrations expire after 10 minutes and are cleared if the backend restarts, so the person must register again after a restart. Password reset codes are stored in MySQL, expire after 10 minutes, and allow up to five attempts.

## Local development

Requirements: Node.js 22.5 or newer.

1. Start the MySQL server. On backend startup, OmniCloud creates the configured database and tables from `schema.sql`, then ensures the GCP, Azure, and AWS profile columns exist. The MySQL user in `.env` must be allowed to create the database and tables.
2. Copy `.env.example` to `.env`; enter your MySQL password, a long random `SESSION_SECRET`, a Google App Password for the Gmail sender, `OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL`, and Azure settings if you configure Azure.
3. From this folder, run `npm install` once, then `npm run dev`.
4. In a second terminal, start the Vite app from `frontend/omnicloud` with `npm run dev`.

On startup, the backend initializes the database from `schema.sql` and then removes legacy unverified user rows and old email-verification codes created by earlier versions. `schema.sql` is the complete final schema for fresh installations. Initialization is idempotent and does not drop tables or disconnect existing AWS connections. For older installations, the backend adds the GCP, Azure, and per-user AWS profile columns to `cloud_connections` without replaying the historical AWS-disconnect migration.

For live email, set `GMAIL_USER` and `GMAIL_APP_PASSWORD` in `.env`. The sender is that Gmail address. Google requires 2-Step Verification to create an App Password. Without those values, development codes are printed in the backend terminal.

Per-user AWS SSO config and credentials files are written beneath `.omnicloud-aws-users` with restrictive file modes; keep this directory private and persistent with the backend. Set `OMNICLOUD_AWS_USER_CONFIG_DIR` to a private persistent directory for deployments. The generated config is ignored by Git.

The Vite development server forwards `/api` requests to port 3001. In production, build the frontend first and run this backend; it serves the built frontend from `frontend/omnicloud/dist`.

## MySQL schema

`schema.sql` is the canonical complete schema. The backend runs its table definitions automatically on startup; the numbered migration files document the evolution of older installations.

## AWS local-profile connection and Terraform provisioning

AWS connections use AWS IAM Identity Center (SSO) profiles configured in the backend host's AWS config file. Each OmniCloud user chooses a profile and completes their own browser sign-in. The backend generates a per-user profile and unique SSO session name so the user's token cache is separate from every other OmniCloud user's cache. It persists the selected profile on that user's connection and checks account identity before every AWS inventory or Terraform operation. AWS tokens stay in the backend user's AWS SSO cache; only short-lived role credentials are passed to Terraform. No customer IAM role, CloudFormation stack, access key, or secret is created or stored by OmniCloud.

1. Install AWS CLI v2.22 or newer on the backend computer and configure an IAM Identity Center SSO session with `aws configure sso-session` (or a named SSO profile) in the AWS config file (`AWS_CONFIG_FILE` or `~/.aws/config`). The backend needs the portal start URL and SSO region; it does not need a fixed account ID or permission set. Alternatively, set `AWS_SSO_START_URL` and `AWS_SSO_REGION` in `.env`.
2. In `backend/.env`, set `AWS_LOCAL_PROFILE_MODE_ENABLED=true` and `AWS_REGION=us-east-1` (or your default AWS API region). `AWS_LOCAL_PROFILE` optionally chooses the initial SSO portal entry. Do not put credentials in `.env`.
3. Restart the OmniCloud backend. Each OmniCloud user opens **Cloud connections** and selects **Connect to AWS**. The backend generates a unique SSO session and runs `aws sso login --sso-session <isolated-session> --use-device-code --no-browser`; OmniCloud opens AWS's access portal and displays the one-time code. After approval, OmniCloud lists the AWS accounts and permission sets assigned to that signed-in user. If there is one choice, it connects automatically; if there are several, the user selects one in OmniCloud.
4. OmniCloud stores the selected portal, account ID, and permission set on that user's connection. Each user's SSO token cache is namespaced by a unique session name; role credentials are resolved for that user and passed to their Terraform child process only. If the session expires, only that user's connection is marked disconnected.
5. In **Cloud services**, create and review a Terraform plan, then explicitly apply it. Before inventory, planning, and applying, OmniCloud verifies the selected user's profile matches the connection's AWS account.

The connection check needs only the SSO profile to authenticate and call STS `GetCallerIdentity`. Terraform needs the AWS service permissions for the selected template. The service pages provide private S3 buckets, `t3.micro` EC2 instances, Single-AZ encrypted MySQL RDS (`db.t3.micro`, 20 GiB), and DynamoDB tables provisioned at 5 read and 5 write units. These are low-cost/free-tier-oriented defaults, not a guarantee of zero charges; account age, eligibility, region, existing usage, and add-on usage affect billing. RDS uses AWS-managed master credentials in Secrets Manager, which may incur a separate charge; deletion skips a final snapshot and deletes database data. DynamoDB point-in-time recovery and secondary indexes are off by default.

AWS inventory and Monitoring require `ec2:DescribeInstances`, `ec2:DescribeSubnets`, `ec2:DescribeSecurityGroups`, `ec2:DescribeKeyPairs`, `s3:ListAllMyBuckets`, `rds:DescribeDBInstances`, `dynamodb:ListTables`, and `dynamodb:DescribeTable`; EC2 image/instance selectors also use `ec2:DescribeImages` and `ec2:DescribeInstanceTypes`. The RDS template also needs the relevant `rds:CreateDBInstance`, `rds:DeleteDBInstance`, `rds:CreateDBSubnetGroup`, `rds:DeleteDBSubnetGroup`, and describe actions. DynamoDB provisioning needs `dynamodb:CreateTable`, `dynamodb:DeleteTable`, `dynamodb:DescribeTable`, and tagging actions for OmniCloud resource tags. EC2 Terraform refresh needs `ec2:DescribeTags` in addition to the selector permissions. The chart’s monthly account actuals need `ce:GetCostAndUsage`; the optional 31-day account forecast needs `ce:GetCostForecast` and Cost Explorer enabled. Grant only the permissions needed for the services being tested. After an administrator updates the permission set, select **Integrate AWS** in Cloud connections to refresh the SSO session, then refresh the service page.

Set `AWS_LOCAL_PROFILE_MODE_ENABLED=false` to disable this integration. Production use requires `AWS_LOCAL_PROFILE_MODE_ENABLED=true`, a backend host with the required AWS CLI profiles configured, persistent private storage for the AWS SSO cache, and a single backend process (or a shared, encrypted session store before horizontal scaling). Profile definitions are provider configuration; each OmniCloud user's login and token cache are isolated. Never expose a developer's credentials or `.aws/credentials` file to users.

## Google Cloud onboarding

Set `OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL` to the real service account used by OmniCloud's Google Cloud backend workload. Enable `iamcredentials.googleapis.com` in the OmniCloud service account's project as well as in customer projects. Do not create or distribute a service-account key. In production, the backend must use Application Default Credentials from workload identity as this configured service account. For local development, authenticate ADC as that same service account with `gcloud auth application-default login --impersonate-service-account="$OMNICLOUD_GCP_SERVICE_ACCOUNT_EMAIL"`; the developer identity must itself be allowed to impersonate it. The customer grants this OmniCloud service account `roles/iam.serviceAccountTokenCreator` only on the per-connection service account generated by the setup flow. See Google's [service account impersonation guidance](https://cloud.google.com/iam/docs/service-account-impersonation) and [generateAccessToken API](https://cloud.google.com/iam/docs/reference/credentials/rest/v1/projects.serviceAccounts/generateAccessToken).

The GCP setup flow is:

1. The signed-in user enters a Google Cloud project ID. OmniCloud creates a tenant-owned setup record and a unique customer service-account email for that connection.
2. OmniCloud displays Cloud Shell commands for the customer to enable IAM Credentials and Cloud Resource Manager APIs, create the service account, grant it `roles/browser` for project verification, and grant the configured OmniCloud service account `roles/iam.serviceAccountTokenCreator` on the customer service account. Compute Engine API and VM permissions are granted separately only if the user chooses the VM service in **Cloud services**.
3. The user runs those commands in the target project and chooses **Verify and connect**.
4. The backend uses Google Application Default Credentials and the Google Auth Library to mint a one-hour impersonated access token. It calls Cloud Resource Manager `projects.get` to confirm the service account can access the selected active project. The token is held only in memory for the request; only project ID and service-account email are stored.

Verification reports missing OmniCloud identity access, missing Token Creator binding, missing project read permission, missing APIs/service account, and inactive or unknown project separately. Setup, verification, and activation queries are scoped to the signed-in `user_id`. The Cloud services screen displays a separate, optional Compute Engine API and VM-permission command block. The account email is shown under the connected project in OmniCloud.

## Microsoft Azure onboarding and Terraform provisioning

Azure customer access uses Azure Lighthouse. Set `OMNICLOUD_AZURE_TENANT_ID` to OmniCloud's real managing Microsoft Entra tenant ID and `OMNICLOUD_AZURE_PRINCIPAL_ID` to the object ID of the OmniCloud service principal used by the backend. Never guess either identifier. This principal must match the backend identity that Terraform and API verification use.

Set `OMNICLOUD_AZURE_AUTH_MODE` to `cli` for local development, or `managed_identity`, `service_principal`, or `oidc` for a deployment host. Local CLI mode requires Azure CLI installed and authenticated to OmniCloud's managing tenant as the configured service principal. A backend-hosted managed identity is preferred in Azure. In service-principal mode, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`, and `ARM_TENANT_ID` belong to OmniCloud's backend runtime only. In OIDC mode, inject `ARM_CLIENT_ID`, `ARM_TENANT_ID`, and a short-lived `ARM_OIDC_TOKEN` at runtime. Never put customer credentials in these settings. The backend obtains short-lived ARM tokens and does not store them.

The Azure setup flow asks the user for a customer subscription ID, customer tenant ID, and existing resource group. OmniCloud generates an ARM template that creates a read-only subscription delegation for discovery and disconnection, plus Virtual Machine Contributor and Network Contributor delegations limited to the selected resource group. A subscription owner (or an identity with the required role-assignment permissions) deploys the template at subscription scope. Compute and Network provider registration is shown separately on the Azure VM service screen because it is only needed if that service is used. OmniCloud verifies that the subscription is enabled, the tenant matches, and the selected resource group is readable before marking the connection connected. Microsoft's [Azure Lighthouse onboarding guide](https://learn.microsoft.com/en-us/azure/lighthouse/how-to/onboard-customer) describes the customer deployment requirements.

Disconnect is blocked while a managed VM or unfinished operation remains. OmniCloud then removes only the two Azure Lighthouse assignments generated for that connection. AWS disconnect removes the saved local-profile link only; it does not modify AWS permissions or sign out of the CLI. GCP disconnect removes its OmniCloud record; its customer-side service-account delegation must be revoked separately to remove cloud permissions.

The Azure Terraform service creates Ubuntu 22.04 Linux VMs in the connected existing resource group, along with a virtual network, subnet, NIC, and network security group. It uses an SSH public key only, has no public IP, and creates no inbound NSG rules. Supported sizes are `Standard_B1s`, `Standard_B2s`, and `Standard_B2ms`. Azure compute, disk, and networking charges may apply. The public key is stored with the deployment to support recovery plans; never submit a private key.

Requirements: Terraform CLI 1.5 or newer on the backend host and outbound HTTPS access to the Terraform provider registry on first initialization. OmniCloud provides an encrypted private S3 bucket template. GCP provides a Debian 12 Compute Engine VM template with an e2-micro, e2-small, or e2-medium machine type, a 10 GB standard boot disk, Shielded VM protections, and no external IP or ingress firewall rule. The app generates provider configuration and does not accept user-submitted HCL or arbitrary Terraform commands. Create and destroy require a reviewed plan and explicit confirmation; plans expire after 15 minutes. Each provider has isolated deployment tables and state folders under `backend/.terraform-state`.

Migration 005 is a historical AWS migration that disconnected previous AWS connections and removed the old CLI-profile column; the automatic schema initializer does not replay it. Migration 006 documents the GCP connection schema change, migration 007 documents GCP Terraform VM tables, and migration 008 documents Azure Lighthouse and VM tables. These schema updates do not delete customer resources or remove Terraform state. Provider deployment metadata, operation status, and plan summaries are stored in MySQL. Terraform plans, generated configurations, and state are separated by provider, user, connection, and deployment under `backend/.terraform-state`. Set `TERRAFORM_STATE_DIR` to a persistent, access-controlled, encrypted volume in deployment. The current Terraform executor is a single-host development implementation, not an isolated ephemeral-worker and remote-state design for production multi-tenant execution. Production needs isolated per-run workers and encrypted, locked remote state. `TERRAFORM_BIN` can point to Terraform when it is not on `PATH`.

Run `npm test` from `backend` to execute AWS, GCP, and Azure onboarding and verification tests. They use mocked cloud clients and do not require live cloud credentials or make live cloud calls. Run `npm run build` and `npm run lint` from `frontend/omnicloud` to check the UI.

## Production settings

Set `NODE_ENV=production`, use a unique `SESSION_SECRET` of at least 32 characters, configure MySQL and Gmail, and serve the app over HTTPS. The session cookie is HTTP-only, SameSite=Lax, and marked Secure in production. Keep `.env` private.

For inventory and monitoring, the AWS IAM Identity Center permission set needs the read actions listed above (AWS list/describe actions commonly require `Resource: "*"`). Monthly actuals need `ce:GetCostAndUsage`; the optional account forecast needs `ce:GetCostForecast`; Cost Explorer must be enabled. After the administrator updates the permission set, choose **Integrate AWS** in Cloud connections to refresh the SSO session, then press **Refresh from AWS** in the service page. The connection check only validates STS identity and does not verify these service permissions.
Terraform provider packages now use a shared local plugin cache under the AWS state directory. Set `TERRAFORM_PLUGIN_CACHE_DIR` to another persistent directory if needed. Provider initialization still requires outbound HTTPS and adequate disk space; a full disk (`ENOSPC`) or blocked registry cannot be repaired by an AWS permission change.
